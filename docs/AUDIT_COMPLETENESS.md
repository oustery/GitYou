**Честная интерпретация цифры.** Для «просмотрщика» GitHub приложение сделано заметно выше среднего: чистый MVVM + Hilt, единый слой ошибок с ключами и локализацией, честная Link-header пагинация на 10 списках, markdown с Prism-подсветкой и нормализацией `<details>`, дифф-вьюер с номерами строк, RU-локаль с полным паритетом ключей и plurals, AMOLED/4 палитры/масштаб текста, отключённые haptics, бейдж непрочитанных, самообновление. Это ~топ-20% клиентов по качеству исполнения.

Но **как «полноценный GitHub-клиент» приложение закрывает свою категорию меньше чем наполовину (47,6%)**, и разрыв сконцентрирован в двух местах: **запись** (открыть/смержить PR, отредактировать issue, создать ветку/файл) и **возврат пользователя** (push, «моя работа», deep links). Отсюда и оценка: продукт отличный «read-only viewer», но не «replacement for the GitHub app» — то есть обещание README пока не выполнено.

### Топ-5 критических недостающих функций

| Место | ID | Что | Почему критично |
|---|---|---|---|
| 1 | **G-001** | Создание гиста не работает: OAuth-флоу не запрашивает scope `gist` (`AuthRepository.SCOPES = "repo read:user notifications"`) → `POST /gists` отвечает 404 | Заявленная фича падает у 100 % пользователей с `error_generic_action` |
| 2 | **G-002** | OAuth-токен со scope `repo` (полный write к приватным репозиториям) лежит **открытым текстом** в `files/gityou.preferences_pb` | Потеря/бэкап устройства = чужой доступ ко всем репозиториям; OWASP MASVS-STORAGE-1 |
| 3 | **G-042** | Боевой путь входа недоступен «из коробки»: `GITYOU_CLIENT_ID` пуст в `gradle.properties`, CI не передаёт `-PGITYOU_CLIENT_ID` | Первый экран требует зарегистрировать собственный OAuth App — отток на онбординге |
| 4 | **G-014** | PR нельзя смержить/закрыть, нет статуса checks и inline review-комментариев | Ревью и мерж — ядро работы с PR; любой мерж уводит в браузер |
| 5 | **G-012** | Нет App Links на `github.com` и приёма share из других приложений | Клиент не открывается из Slack/почты/браузера — внешний трафик теряется целиком |

Плюс два «тихих» дефекта данных, которые я вынес в High, потому что они не видны глазами: **G-003** (в PR с >100 файлами дифф молча обрезается — решение о мерже принимается по неполной картине) и **G-021** (Release/Discussion-уведомления открывают несуществующий issue).

### Рекомендации по приоритету

1. **Сначала «не врать»** (1–2 недели, ~4 человеко-дня + QA): G-001, G-042, G-003, G-021, G-004, G-005, G-002. Это либо падающая фича, либо ошибка данных, либо утечка секрета — дешёво и без продуктовых решений.
2. **Потом «закрыть ядро категории»** (2–4 недели): G-014 (мерж/checks), G-008/G-009 (правка и триаж issues), G-010 («моя работа»), G-007/G-012 (навигация и вход извне).
3. **Только потом «инфраструктура удержания»**: push (G-015, XL) имеет смысл после G-010 и G-017 (телеметрия), иначе нечего пушить и нечем мерить эффект.

Распределение находок: **42** всего — Critical 2, High 17, Medium 18, Low 5 (по типам: CORE 16, UX 10, TECH 6, SEC 3, REG 3, BUS 2, FUTURE 2).
